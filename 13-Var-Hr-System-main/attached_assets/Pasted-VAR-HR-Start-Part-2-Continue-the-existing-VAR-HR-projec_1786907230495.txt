PART 2 — Production Readiness Foundations

Part 1 is complete.

Part 2 is now focused on moving VAR HR from the provider-neutral/demo-safe implementation toward real production-ready infrastructure.

The main Part 2 areas are:

1. Real Authentication

Replace the current development-only workspace identity mechanism with the project's intended real authentication architecture.

Requirements:

- Do not invent fake authentication.
- Do not hard-code a production user.
- Do not randomly select an authentication provider.
- Preserve the existing provider-neutral architecture where practical.
- Keep the development/demo adapter available for local development if it is intentionally part of the existing design.
- Establish a clear authenticated user identity on the server.
- Derive company and role from the authenticated identity/server-side data.
- Never trust client-supplied company IDs, roles, employee IDs, or permission headers as authoritative production identity.
- Preserve the existing tenant and role authorization boundaries already implemented in Part 1.
- Ensure unauthenticated requests fail safely.
- Ensure authenticated users can only access resources permitted by their company, role, and capabilities.

Before implementing authentication, inspect the existing authentication boundary and explain from the code which integration point is intended.

Do not introduce a provider merely because it is convenient.

If the repository already specifies the provider/integration to use, follow that specification.

If the production authentication provider is genuinely unspecified, do not invent one. Document the exact blocker in the hand-off and implement only the provider-independent pieces that can safely be completed.

---

2. Authenticated Role Contexts

Part 2 must establish a reliable foundation for real role-based sessions.

The system must support the existing VAR HR roles without weakening their boundaries:

- Platform Owner
- Company Owner
- Manager
- Employee

The authenticated session must determine the user's actual identity and role.

Do not rely on UI-only role hiding.

Authorization must remain enforced server-side.

Verify that:

- Company Owner cannot access another company's data.
- Manager is restricted to the appropriate company/manager scope.
- Employee is restricted to their own permitted employee data.
- Platform Owner retains platform-level capabilities.
- Unauthorized API requests return appropriate access errors.
- UI navigation and available actions reflect the authenticated capabilities.

---

3. Session / Workspace Initialization

After authentication is established:

- The application should initialize the correct workspace from the authenticated user.
- Remove dependence on manually supplied production workspace headers.
- Preserve the development adapter only where explicitly appropriate.
- Ensure refresh/reload does not lose the authenticated workspace context.
- Ensure logout clears the authenticated state correctly.
- Handle loading, unauthenticated, unauthorized, and expired-session states cleanly.
- Do not expose another user's workspace while authentication state is loading.

---

4. Production-Safe Security Boundary

Audit the existing request boundary after authentication is connected.

Specifically verify:

- Tenant isolation.
- Role isolation.
- Employee identity isolation.
- Protected API routes.
- Device synchronization permissions.
- Payroll/report permissions.
- Subscription/device/platform-owner permissions.
- Any route that currently consumes workspace/role headers.
- Any route that derives authorization from client-controlled values.

The goal is:

Client identity → authenticated server identity → database lookup → authorization → data

not:

Client-supplied role/company/employee → authorization
