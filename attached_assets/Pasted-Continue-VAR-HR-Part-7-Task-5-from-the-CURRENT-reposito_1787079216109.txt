# Task 5 — Complete the Remaining Part 7 Frontend

The backend functionality for schedules, holidays, biometric providers/sync, and employee HR records is already implemented.

Task 5 is to expose the remaining functionality through a complete, usable VAR HR frontend while preserving the existing UI architecture.

## 1. Employee Schedules UI

Add the appropriate existing-architecture UI for authorized users to:

- view employee schedules
- create schedules
- edit schedules
- assign a schedule to an employee
- see the employee's effective schedule
- handle working/non-working days
- configure start/end times
- support overnight schedules such as 22:00 → 06:00

Respect existing role permissions.

Employee:
- view their own applicable schedule where appropriate
- cannot administer schedules

Manager:
- manage/view schedules only for employees in their authorized scope

Owner/authorized HR:
- manage company schedules and employee assignments

Do not create a new permission system.

## 2. Company Holidays UI

Add the appropriate UI to:

- list company holidays
- create a holiday
- edit a holiday
- delete a holiday where permitted

Show useful validation/errors.

Prevent duplicate/conflicting holiday entries according to the existing API behavior.

Keep all company data tenant-scoped.

## 3. Biometric Devices / Providers UI

Expose the existing biometric provider/device functionality through the UI.

Authorized users should be able to:

- view available biometric providers/devices
- view connection/status information
- test a provider/device connection where the existing API supports it
- trigger employee synchronization where already supported
- trigger attendance/event synchronization where already supported
- view synchronization results/history

Do not redesign or rewrite the biometric backend from Task 2.

Do not add physical-device support that does not already exist.

Clearly distinguish mock/testing behavior from real hardware integration where applicable.

## 4. Sync History UI

Provide a usable view for synchronization history.

Show appropriate non-sensitive information such as:

- provider/device
- operation
- status
- timestamp
- success/failure
- counts/results
- error information where appropriate

Do not expose credentials, secrets, tokens, or sensitive device configuration.

Support loading, empty, error, and retry states.
