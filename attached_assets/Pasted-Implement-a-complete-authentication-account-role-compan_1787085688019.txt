Implement a complete authentication, account, role, company, subscription-limit, and employee-login system for VAR HR from scratch.

IMPORTANT:
There is currently NO login page and NO existing authentication/account system in the VAR HR application.

Do NOT assume an existing authentication system.
Do NOT try to modify or extend a nonexistent login system.

This is a new foundational system that must be integrated into the existing VAR HR architecture.

Tasks 1–7 of the existing HR functionality are already implemented. Preserve all existing HR functionality and do not rewrite attendance, payroll, schedules, holidays, biometric synchronization, reports, or HR records.

==================================================
1. FOUR ACCOUNT LEVELS
==================================================

Build exactly four account levels:

1. Platform Owner
2. Company Owner
3. Company Staff / Admin users
   - Manager
   - Supervisor
   - HR
   - Custom permission-based staff accounts
4. Employee

The system must keep Platform Owner completely separate from Company Owners.

==================================================
2. PLATFORM OWNER
==================================================

The Platform Owner represents the VAR HR platform owner.

This is the highest-level account.

Platform Owner can:

- Create companies.
- Edit companies.
- Activate/deactivate companies.
- Create the Company Owner account for each company.
- Set the company's subscription/employee limit.
- View company information.
- View company employee usage against the subscription limit.
- Manage company subscription status/limits.
- Manage Company Owner accounts.

IMPORTANT:

Only Platform Owner can create a Company Owner account.

A Company Owner must NOT be able to create another Company Owner.

Company data must always remain isolated from other companies.

Platform Owner is the only role allowed to operate across companies.

==================================================
3. COMPANY OWNER
==================================================

Each company has its own Company Owner.

The Company Owner account is created ONLY by the Platform Owner.

Company Owner can manage only their own company.

Company Owner can:

- View company information.
- Manage employees.
- Create Manager/Supervisor/HR/staff accounts.
- Assign permissions to those accounts.
- Manage branches.
- Manage biometric devices.
- Manage schedules.
- Manage holidays.
- Manage attendance-related administration.
- View permitted payroll/report information.
- Manage HR records according to permissions.
- View employee login credentials according to the employee-credential rules below.

Company Owner must never be able to access another company's data.

==================================================
4. MANAGER / SUPERVISOR / HR / STAFF ACCOUNTS
==================================================

Do NOT create unnecessary rigid roles if the existing architecture supports permissions.

The Company Owner should be able to create staff accounts and assign a display role such as:

- Manager
- Supervisor
- HR

The actual access should be controlled through explicit permissions.

For example:

Employee Management
Attendance
Leaves
Permissions
Schedules
Holidays
Payroll
Reports
HR Records
Biometric Devices
Sync History
etc.

The Company Owner decides which permissions each staff account receives.

A staff account:

- belongs to exactly one company.
- cannot access another company.
- cannot create a Company Owner.
- cannot modify platform subscription limits unless explicitly allowed by the platform.
- cannot automatically receive salary/payroll access simply because the account is called Manager or HR.
- only sees the modules and actions granted by its permissions.

Build the permission model so it can be extended later without rewriting authentication.

==================================================
5. EMPLOYEE ACCOUNTS
==================================================

Employees are different from administrative/staff accounts.

Employee accounts are created automatically as part of the employee/biometric onboarding flow.

The employee does NOT choose their username.

The system generates the username from:

BIOMETRIC DEVICE/BRANCH CODE + EMPLOYEE BIOMETRIC NUMBER

Example:

Company has a main branch/device.

The first biometric device/branch registered in the system receives:

A

Employee biometric number:

20

Generated username:

A-20

Another biometric device/branch registered later receives:

B

Employee biometric number:

20

Generated username:

B-20

Therefore:

A-20
B-20

are different employees even though their biometric numbers are both 20.

==================================================
6. BIOMETRIC CODE GENERATION
==================================================

The code is assigned automatically in the order that biometric locations/devices are first registered in VAR HR.

First registered biometric source:

A

Second:

B

Third:

C

and so on.

Do NOT manually ask the user to enter A/B/C.

The system must generate it.

IMPORTANT:

Use the existing biometric architecture from Part 7.

Do not rewrite the biometric provider system.

The biometric code must be persisted and remain stable.

If a device/source is disabled later, its code must NOT be reused for another source.

Never change an existing employee's username because the device code sequence changes.

If the system currently models the biometric identity at device level, use that existing architecture consistently.

If the current model clearly represents a branch/location as the biometric identity, use the branch-level identity instead.

Do not create duplicate competing concepts unnecessarily.

==================================================

Employee username format:

<CODE>-<BIOMETRIC_NUMBER>

Examples:

A-20
A-21
A-100
B-20
C-7

The username must be unique within the authentication system.

Prevent collisions.

If the same biometric number exists on the same biometric source, do not silently create a second account.

The employee account must remain linked to:

- company
- employee
- biometric source/device
- biometric employee number

==================================================
8. EMPLOYEE PASSWORD
==================================================

When the employee account is created:

Generate a random 6-digit numeric password.

Example:

583214

Requirements:

- exactly 6 digits.
- cryptographically/randomly generated using the project's secure server-side facilities.
- never generated by the frontend.
- never use predictable sequences.
- never use the employee biometric number as the password.
- never use the same password for every employee.

Store the password securely.

Do NOT store plaintext passwords in the database.

Use a secure password hashing mechanism.

==================================================
9. EMPLOYEE CREDENTIAL DISPLAY
==================================================

Company Owner or staff users with an explicit employee-credential permission may retrieve/display employee login credentials according to the permission model.

The system should allow an authorized user to obtain the employee's:

Username
Temporary/generated password

so they can send the credentials to the employee.

IMPORTANT SECURITY REQUIREMENT:

Do NOT store the plaintext password permanently just so it can be displayed later.

Implement this safely.

Preferred behavior:

- Generate the initial password.
- Display it once to the authorized administrator after account creation.
- Allow a controlled "Reset Employee Password" action for authorized users.
- When reset is performed, generate a new 6-digit password.
- Display the newly generated password to the authorized user once.
- Store only the password hash.

If the current UX requires an administrator to retrieve credentials later, design a secure reset/reveal workflow rather than storing plaintext passwords.

Record password reset events in an audit-friendly way without storing the plaintext password.

13. COMPANY EMPLOYEE LIMIT
==================================================

The Platform Owner assigns each company a maximum employee count based on its subscription.

Example:

Company A:
Employee limit = 100

Company currently has:
97 employees

The system allows:
3 more employees.

When the limit is reached:

Do NOT allow creation/import/onboarding of additional employees.

Show a clear error explaining that the employee limit has been reached.

Employee administrative/staff accounts should NOT accidentally consume the employee quota unless the business model explicitly defines them as employees.

Keep the subscription employee count concept separate from administrative account count.

Also account for employees created through:

- manual creation
- biometric synchronization
- employee import

All employee-creation paths must respect the same subscription limit.

Do not bypass the limit through biometric sync or import.
