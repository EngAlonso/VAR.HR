PART 4 — BIOMETRIC DEVICES & GPS

Part 4 has two main areas:

1. Biometric attendance devices
2. GPS/location-based attendance

The goal is to establish a solid architecture for connecting physical attendance devices and location-based attendance without prematurely implementing the later attendance-rules, overtime, payroll, or reporting systems.

---

1. BIOMETRIC DEVICE MANAGEMENT

First inspect the existing database, API architecture, contracts, and UI to determine what already exists.

Do not assume a device vendor.

Do not invent a proprietary protocol.

Do not hard-code support for a specific manufacturer unless the repository already specifies one.

The system should be designed around a provider/device adapter architecture so different biometric devices can eventually be supported through a common VAR HR interface.

Conceptually:

VAR HR
↓
Biometric Device Integration Layer
↓
Device Adapter
↓
Physical Device

Different devices should eventually be able to use different adapters while the rest of VAR HR sees a consistent interface.

---

2. DEVICE REGISTRATION

Create or complete the company-level device management functionality.

An authorized company user should be able to manage biometric devices.

A device should have appropriate information such as:

- Device name
- Device type/vendor
- Connection information
- IP/hostname where applicable
- Port where applicable
- Device identifier
- Company ownership
- Status
- Last synchronization time
- Connection/health state

Do not store credentials insecurely.

Do not expose sensitive connection credentials to normal frontend responses.

Do not invent a vendor-specific credential format if the actual vendor has not been selected.

If encryption/secrets infrastructure is not available, document the limitation rather than creating an insecure implementation.

---

3. DEVICE LIST

Authorized users should be able to see the biometric devices belonging to their company.

The UI should show useful operational information such as:

- Device name
- Type/vendor
- Status
- Last sync
- Connection state
- Number of synchronized employees where supported

The device list must respect company isolation.

A company must never see another company's devices.

Employees should not automatically receive device-management access.

---

4. DEVICE CONNECTION TEST

Where technically possible through the existing architecture, provide a way for an authorized user to test whether a registered device is reachable.

The result should clearly communicate:

- Connected
- Unreachable
- Authentication failure
- Unsupported device
- Configuration error
- Unknown connection error

Do not fake successful connections.

If no actual device protocol/vendor is available in the repository, create the provider-neutral integration boundary and clearly document that physical-device testing requires a real supported device/adapter.

---

5. EMPLOYEE ↔ DEVICE MAPPING

The system needs a safe way to associate employees with biometric device identities.

Do not assume the employee's database ID is automatically the biometric device ID.

A device may use its own employee identifier.

The architecture should therefore support a mapping similar to:

Company Employee
↓
VAR HR Employee ID
↓
Device-specific Employee ID
↓
Biometric Device

An employee may eventually exist on more than one device.

The mapping must remain company-scoped.

---

6. EMPLOYEE SYNCHRONIZATION

The long-term workflow should support:

VAR HR
→ send employee to device

and:

Device
→ return attendance/biometric events to VAR HR

For this phase, implement only what can be safely supported by the available device integration information.

Do NOT pretend that synchronization works if no actual device adapter exists.

If there is no specified biometric vendor/protocol, establish the integration interfaces, database model, API boundary, and UI required for future adapters, then document the exact remaining dependency.

---

7. BIOMETRIC ATTENDANCE EVENTS

The system should have a clear internal representation for raw device events.

A raw event may contain information such as:

- Device ID
- Device employee ID
- Timestamp
- Event type
- Direction
- Raw device payload where appropriate

Keep raw device data separate from the already-processed attendance record.

Conceptually:

Biometric Device
↓
Raw Attendance Event
↓
Employee Mapping
↓
Attendance Processing
↓
Attendance Record

Do not duplicate the existing Attendance system from Part 3.

Part 3 remains the source of truth for the employee-facing attendance history.

Part 4 should provide the integration layer feeding that system.

---

8. DUPLICATE EVENTS

Biometric devices may send the same event more than once.

The system must prevent accidental duplicate attendance events where appropriate.

Use a safe idempotency strategy.

Do not blindly insert the same event repeatedly.

Do not delete legitimate events just because timestamps are similar.

Document the chosen deduplication strategy.

---

9. GPS ATTENDANCE

Add the foundation for location-based attendance.

The system should be able to capture:

- Latitude
- Longitude
- Timestamp
- Employee
- Attendance action
- Accuracy where available
- Location source where appropriate

Do not store location data for users who did not perform a location-based attendance action.

Respect company and employee scope.

---

10. LOCATION RULE FOUNDATION

The system should support the concept of company-defined attendance locations/geofences without implementing the full attendance-rules engine.

A company may eventually define:

- Office/site name
- Latitude
- Longitude
- Allowed radius
- Active/inactive state

For example:

Office A
→ Latitude/Longitude
→ Allowed radius: 200m

The system can then determine whether a GPS attendance action occurred within the configured location.

Do not implement complex scheduling or payroll consequences here.

Those belong to later phases.

---

11. GPS VALIDATION

Where GPS attendance is implemented, validate:

- Location exists.
- Coordinates are valid.
- Timestamp is valid.
- Employee is authorized.
- Employee belongs to the company.
- Attendance action is allowed.
- Location is within the configured allowed area when geofencing is active.

Do not trust coordinates supplied by an unauthorized user.

Server-side validation is required.

---

12. PRIVACY AND SECURITY

Location information is sensitive operational data.

Follow the existing authorization architecture.

Employees should only be able to access their own location-based attendance information.

Managers should only access employees within their authorized scope.

Company Owners should have company-level access.

Cross-company access must be rejected.

Do not expose raw GPS data through endpoints that do not need it.

Do not log unnecessary personal/location information.
