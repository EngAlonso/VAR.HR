# Task 4 — Complete Employee HR Records

The Employee HR Record API boundary was implemented in Task 1.

Now complete the actual HR-record functionality so authorized users can manage and view a complete employee HR profile through the existing VAR HR architecture.

## 1. Employee HR profile

Complete the existing HR-record model/API behavior using the fields already defined by the current schema and contracts.

The HR record should support the employee information already established by the project, such as:

- personal/employee information
- employment information
- job/department information
- manager relationship
- hiring/employment dates
- salary information where already supported
- emergency/contact information where already supported
- HR notes/documents/metadata where already supported

Do NOT invent a completely new employee model.

Use the existing employee and HR-record schemas.

If a required field already exists elsewhere in the employee model, reuse it rather than duplicating it in the HR record.

## 2. Employee access

An Employee may:

- view their own authorized HR information.
- never view another employee's HR record.
- never modify confidential/company-level HR settings.

Respect the existing authorization helpers.

## 3. Manager access

A Manager may:

- view HR records for employees within their authorized management scope.
- update only fields the existing permission model allows.
- never access employees outside their scope.
- never gain company-wide access simply because they are a Manager.

Do not create new permission semantics unless the existing system has no suitable permission for the required operation.

## 4. Owner / authorized HR access

Owner or authorized HR users may:

- view employee HR records within their company.
- create/update HR information where allowed by the existing model.
- manage employee employment information according to existing permissions.

Keep all queries company-scoped.

## 5. Developer access

Developer must remain separate from Owner.

Developer access must NOT automatically expose:

- salaries
- payroll information
- confidential employee HR information

Only expose technical/integration information where the existing permission model explicitly allows it.

## 6. Tenant isolation

Every HR-record operation must verify company ownership.

Test:

- Employee A cannot access Employee B in the same company when unauthorized.
- Manager cannot access an employee outside their scope.
- Company A cannot access Company B's employee/HR record.
- Invalid employee/HR IDs return the normal validation/not-found behavior instead of 500.

Do not leak cross-company resource existence.

## 7. Data consistency

Ensure HR records remain correctly associated with their employee and company.

Prevent:

- duplicate HR records where the model expects one record per employee.
- HR records attached to employees from another company.
- orphaned records where existing relationships require an employee.
- inconsistent manager/company relationships.

Use database constraints or existing validation patterns where appropriate.

## 8. Salary confidentiality

Treat salary/compensation information as confidential.

Verify that:

- unauthorized Employee cannot see another employee's salary.
- unauthorized Manager cannot see salary information outside their permitted scope.
- Developer does not automatically receive salary visibility.
- Owner/authorized HR retains the intended access.

Do not expose confidential fields through an endpoint that should return only non-sensitive employee information.

If the existing API contract needs separate response shapes for sensitive/non-sensitive information, make the smallest contract-safe change and regenerate the clients.

## 9. API behavior

Use the existing HR-record endpoints from Task 1.

Do not create duplicate endpoints.

Use:

- existing Zod validation
- existing OpenAPI contract
- existing authorization helpers
- existing tenant-scoping patterns

If the current contract is insufficient for a required HR-record operation, make the smallest necessary OpenAPI change and regenerate the generated outputs.

Do not manually edit generated files.
