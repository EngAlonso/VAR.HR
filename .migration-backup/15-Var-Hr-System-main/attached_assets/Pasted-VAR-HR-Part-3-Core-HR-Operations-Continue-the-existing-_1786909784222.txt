A. ATTENDANCE

Audit the existing Attendance implementation first.

Do not assume it is missing just because the feature exists in the UI. Determine what is already implemented and what is incomplete.

The goal is a reliable daily attendance foundation.

Attendance records

The system should support:

- Employee attendance records.
- Check-in.
- Check-out.
- Attendance history.
- Date-based filtering.
- Employee-based filtering.
- Company/manager scope.
- Correct role-based visibility.
- Attendance status.
- Missing check-in/check-out states.
- Present/absent/late/early-leave concepts where already supported by the current data model.

Do not invent complicated attendance rules yet.

If late/early/absence calculations depend on the future Rules module, preserve the existing boundary and document the dependency rather than duplicating the rules engine here.

Attendance corrections

Where the existing system supports corrections:

- Ensure authorized users can correct attendance.
- Record who made the correction.
- Preserve the original information where the current architecture supports audit history.
- Prevent employees from modifying records they are not allowed to modify.
- Preserve server-side authorization.

Employee scope

Verify:

Employee

- Can see only their own attendance data.
- Cannot modify company-wide attendance.
- Cannot access another employee's records.

Manager

- Can see only employees within their authorized management scope.
- Can perform only the attendance actions allowed by their capabilities.

Company Owner

- Can manage attendance for their company according to existing capabilities.

Platform Owner

- Retains platform-level access according to the existing authorization model.

Do not rely on frontend hiding alone.

Every important boundary must be enforced by the API.

B. LEAVE & PERMISSIONS

Audit the existing leave and permission implementation.

The system should provide a coherent workflow for:

Leave types

Support the existing architecture for multiple leave types.

Examples may include:

- Annual leave
- Sick leave
- Unpaid leave
- Other company-defined leave types

Do not hard-code a fixed list if the current architecture already supports configurable types.

Leave balances

Each employee should have a leave balance where the existing data model supports it.

Verify:

- Balance visibility.
- Used balance.
- Remaining balance.
- Correct employee scope.
- Safe updates after approved requests.

Do not invent payroll deductions or complicated leave accounting rules yet.

Those belong to later stages if not already implemented.

Leave requests

Employee should be able to:

- Create a leave request.
- Select the appropriate leave type.
- Select dates.
- Provide a reason/notes where supported.
- See request status.
- See previous requests.

Manager/authorized approver should be able to:

- Review requests within their scope.
- Approve.
- Reject.
- Provide/review rejection reason where supported.
- See the resulting status.

Company Owner should retain company-wide approval capabilities according to the existing authorization model.

Permission requests

Implement/audit the same coherent workflow for attendance permissions:

Employee:

- Submit permission request.
- See status.
- See previous requests.

Manager/authorized approver:

- Review.
- Approve.
- Reject.
- Record rejection reason where supported.

Owner:

- Company-wide management according to existing permissions.

Again, server-side authorization is mandatory.

7. VALIDATION

Do not stop at typechecking.

After implementation, validate the actual workflows.

At minimum verify:

Attendance

- Employee sees own attendance.
- Employee cannot access another employee's attendance.
- Manager sees only authorized employees.
- Owner sees company attendance.
- Unauthorized modification is rejected.
- Authorized correction works.
- Check-in/check-out behavior works where already supported.

Leave

- Employee sees request status.
- Manager receives/sees the request within scope.
- Manager can approve.
- Manager can reject.

Permission

- Employee sees its status.
- Manager sees the request within scope.
- Manager can approve.
- Manager can reject.
- Unauthorized approval is rejected.
- Cross-company access is rejected.

Also validate:

- Relevant frontend build.
